Governing Claude: Inference hooks vs Bedrock Guardrails

Two surfaces, two control models — bullet-point version for engineers.

The core idea

  • There are two different doors into the same model, and each has its own enforcement story.
  • Employees chatting (claude.ai, Claude Code, Cowork) → governed by Inference hooks — their pipe, our opinion.
  • Applications calling the API on AWS (Bedrock) → governed by Bedrock Guardrails — our pipe, our rules.

Inference hooks — their pipe, our opinion

  • Claude Enterprise feature. The checkpoint lives inside Anthropic's pipeline, before the model runs.
  • You don't call Anthropic — Anthropic calls you: a signed HTTPS POST with the conversation, to a public endpoint you host.
  • Your server answers HTTP 200 with {"action":"allow"} or {"action":"deny","deny_reason":"..."}. Deny → the user sees your reason. Protocol: endpoint docs.
  • With tool-call validation on, Claude's tool calls get the same allow/deny treatment before they run.
  • Three states, set only in the console (claude.ai → Organization settings → Data and privacy → Inference hooks, Owner role — configuration docs):
    • Off — Enforce verdicts off; your server is never contacted.
    • Inform (Shadow mode) — your server receives everything and votes; the vote is ignored; nobody is blocked. For tuning policy on real traffic, with a rollout %.
    • Enforce — a deny blocks the user. Failure handling decides what happens when your server is down: fail-open or fail-closed.
  • No API for any of this. The Admin API covers members, workspaces, keys, spend limits — not hooks. Flipping enforcement is a human in the console.
  • What the third-party side can do — the asymmetry:
    • You can always soften: your server deciding "evaluate but allow" is a runtime inform mode you own, per request, per user, per app.
    • You can never harden: Shadow ignores your deny; Off never calls you. No server-side trick forces blocking.
    • Errors are not a lever: non-200 or timeout = webhook failure → failure-handling policy applies, and sustained failures trip a circuit breaker that stops the calls entirely.
  • Rules that bite: a deny is HTTP 200, never an error · ~5s budget for the whole exchange · bodies up to 64 MiB · endpoint must be public HTTPS, no tunnels · traffic comes from 160.79.106.0/24 (IP ranges) · every denial lands in the Activity Feed with your reference_id.
  • Scope: claude.ai, Claude Code, Cowork only. Not Bedrock, not Vertex.

Bedrock — our pipe, our rules

  • The model endpoint lives in your AWS account: your request path, your VPC, your IAM, your gateway in front.
  • Guardrails are resources you create and attach per call — not something built into the pipe:
    • Managed via API: CreateGuardrail / UpdateGuardrail, versioned, Terraform-able.
    • Applied on InvokeModel/Converse, or evaluated standalone with ApplyGuardrail.
    • Enforce = block action · Inform = detect-only · Off = don't attach the guardrail.
    • No guardrails at all is a valid configuration — the option claude.ai never offers its users.
  • Who can flip the dial is plain IAM — no single console Owner, fully automatable.
  • With Kong AI Gateway Enterprise, enforcement sits at the gateway: the AI AWS Guardrails plugin applies a Bedrock guardrail to requests and responses (guardrail ID + version + region, IAM-role auth from 3.12 — how-to). Enforce/inform/off becomes a decK diff or a Konnect API call.

Where the check can live — and why you'd put it there

A prompt travels app → gateway → provider → model. A guardrail can be bolted on at any of those hops, and the placement decides what it can see, who can bypass it, and who pays the latency:

  • In the application (SDK call, e.g. ApplyGuardrail from code) — why here: most context (the app knows the user, the feature, the tenant), so the finest-grained decisions. why not: every team must implement and update it; one forgetful service = a hole. Policy drifts across codebases.
  • At the gateway (Kong plugin) — why here: one choke point every app already passes through, so policy is inherited with zero code changes, owned by one team, versioned as config. why not: it only sees traffic that actually goes through it — a workload calling Bedrock directly around Kong is invisible to it.
  • At the provider, attached to the call (guardrailIdentifier on InvokeModel/Converse) — why here: the check rides with the request itself, gateway or not. And IAM can make it mandatory: a policy condition on the guardrail identifier can deny any model call that doesn't attach it, closing the "bypass the gateway" hole. why not: still your caller's responsibility to wire, and the IAM trick needs discipline in account design.
  • Inside the provider's pipeline, before the model (inference hooks) — why here: the only placement that covers surfaces you don't proxy at all — employees typing into claude.ai or Claude Code. Nobody can route around it, because the pipe isn't yours to route around. why not: precisely for the same reason, the ceiling isn't yours either: console-only, Owner role, no API.

Rule of thumb for the class: the further from the app you check, the broader the coverage and the weaker the context — and the question "can someone bypass it?" is answered by who owns the hop, not by the tool.

Kong side — the AI AWS Guardrails plugin

What it is.

  • A Kong Enterprise plugin (ai-aws-guardrails, Gateway ≥ 3.11, AI Gateway Enterprise license) that sits on the same route as AI Proxy / AI Proxy Advanced and applies a Bedrock guardrail to the traffic passing through the gateway.
  • It separates two things that are often confused: the policy (the guardrail — content filters, denied topics, PII rules — a versioned resource living in your AWS account) and the enforcement point (Kong, where every request already flows).

How it does it.

  • On each request, the plugin extracts the prompt text from the body (text_source: just the user messages, or the whole exchange), sends it to the Bedrock Guardrails service in your region, and gets a verdict back — before the model is ever called.
  • With guarding_mode: OUTPUT or BOTH, it does the same to the model's response on the way back out.
  • Streaming responses can't be checked token by token economically, so it buffers response_buffer_size tokens and checks per chunk — smaller buffer = faster blocking, more guardrail calls (and cost).
  • On a violation, Kong answers the client with a policy-violation error itself; for input violations the upstream model is never reached, so nothing sensitive leaves and no tokens are paid for.
  • Auth to AWS is IAM: a role the data plane assumes (aws_assume_role_arn, 3.12+) or static keys. log_blocked_content (3.14+) records what was blocked for audit.

Why it's built this way.

  • Why at the gateway: every app behind Kong inherits the policy with zero code changes — one team owns it, no SDK to update in ten services, no app can "forget" to apply it.
  • Why the policy lives in AWS, not in Kong: guardrails are versioned, auditable AWS resources (CreateGuardrail/UpdateGuardrail, Terraform-able), evaluated by AWS's own classifiers — Kong doesn't reimplement content analysis, it just decides where the check happens.
  • Why check input before proxying: blocking at the gate means the sensitive prompt never reaches the model provider at all — cheaper (no tokens) and stronger (no data egress), the same "check at the source" idea inference hooks apply on Anthropic's side.

The config — the guardrail is created in AWS first (aws bedrock create-guardrail), which returns the ID and version the plugin needs; then both plugins go in via decK (Kong how-to):

_format_version: "3.0"
plugins:
  # 1. Route the traffic to the model
  - name: ai-proxy-advanced
    config:
      targets:
        - route_type: llm/v1/chat
          model:
            provider: bedrock          # or openai/anthropic/etc.
            name: anthropic.claude-sonnet-4-5
            options:
              bedrock:
                aws_region: "${{ env "DECK_AWS_REGION" }}"

  # 2. Attach the Bedrock guardrail to that traffic
  - name: ai-aws-guardrails
    config:
      guardrails_id: "${{ env "DECK_GUARDRAILS_ID" }}"        # from create-guardrail
      guardrails_version: "${{ env "DECK_GUARDRAILS_VERSION" }}"  # e.g. DRAFT or "1"
      aws_region: "${{ env "DECK_AWS_REGION" }}"
      aws_assume_role_arn: "${{ env "DECK_GUARDRAILS_ROLE_ARN" }}"  # IAM role (3.12+); or aws_access_key_id/aws_secret_access_key
      guarding_mode: BOTH              # INPUT | OUTPUT | BOTH (default: input only)
      text_source: concatenate_all_content   # or concatenate_user_content
      response_buffer_size: 50         # tokens buffered before checking, streaming
      log_blocked_content: true        # 3.14+: log what was blocked, for audit
  • Enforce / inform / off on this surface — all config pushes, no console, and here's why each works:
    • Enforce — plugin enabled, guardrail filters set to block: the gateway answers the violation itself, the model is never called.
    • Inform — keep the plugin on, flip the guardrail's filters to detect-only in AWS (UpdateGuardrail): the same evaluation runs and is logged/traced, but the verdict carries no block action — identical to inference hooks' Shadow mode, just controlled by API instead of a console human.
    • Off — enabled: false on the plugin (one decK diff or Konnect API PATCH): the guardrail call disappears from the request path entirely — zero added latency, zero guardrail cost.
  • Why versions matter for rollout: point guardrails_version at DRAFT while tuning, pin a published number for prod. Enforcement rollback becomes changing one string in config — reviewable, diffable, instant.
The one-sentence takeaway: Inference hooks inspect at the source, before the prompt reaches the model, inside Anthropic's pipeline — so the ceiling is held by a human in their console and you only control what happens below it. On Bedrock the pipeline is yours, so control is total and API-driven — including the choice to have no guardrails at all.

Which one do you need?

  • Employees using Claude apps → inference hooks. Compliance owner holds the console ceiling; engineering holds the verdict server below it.
  • Your products calling Claude on Bedrock → Bedrock Guardrails through the gateway, config-as-code end to end.
  • A company with both kinds of traffic needs both — one does not cover the other.
